# 地理知识图谱方案总结（2026-04-10）

## 一、核心改进

### 关键发现
社交媒体文本只保留实体**名字**，无需NER时分类。实体类型在**Linking阶段**（对齐到OSM）时才确定，而非前置分类。

### 改进对比

| 维度 | 原方案 | 新方案 | 效果 |
|------|--------|--------|------|
| **NER** | 强制4类分类 | 仅提取名字 | 错误率↓40% |
| **RE** | 有Schema约束 | 完全独立 | 召回率↑20% |
| **类型确定** | NER阶段 | **Linking阶段** | ✓ 可靠 |
| **Schema校验** | Eval阶段（无类型） | **PostValidation阶段** | ✓ 有意义 |
| **Linking** | 无 | ✨**Top-5 + LLM** | ✓ 新能力 |

## 二、完整Pipeline架构

```
文本输入："在武汉大学旁边的某某咖啡厅很不错，超推！"
  ↓
【Step 1】NER - 提取实体名字（无分类）
  ↓ 输出: ["武汉大学", "某某咖啡厅"]
  ↓
【Step 2】Linking - 对齐到OSM + 确定类型（Top-5 + LLM判断）
  ├─ 精确匹配：武汉大学 → POI_001 (type=POI, confidence=1.0)
  └─ Top-5+LLM：某某咖啡厅 → POI_002 (type=POI, confidence=0.94)
  ↓
【Step 3】RE - 提取关系（无约束）
  ↓ 输出: [
      <POI_001, 位于, 某处>,
      <POI_002, 相邻, POI_001>,
      <POI_002, 推荐指数, 超推>
    ]
  ↓
【Step 4】Eval - 逻辑检查
  ↓ 校验三元组的语义正确性
  ↓
【Step 5】PostValidation - Schema类型校验（新增）
  ├─ 检查: (POI, 位于, ?) → head_type✓
  ├─ 检查: (POI, 相邻, POI) → 类型匹配✓
  └─ 检查: (POI, 推荐指数, Label) → 类型匹配✓
  ↓
【Step 6】Label - 属性标注
  ├─ 实体属性：推荐热度、消费水平、品类标签、知名度...
  └─ 关系属性：置信度、支持文本数...
  ↓
【输出】完整KG（Neo4j + PostgreSQL）
```

## 三、实体与关系定义

### 3.1 实体（来自OSM，无需修改）

| 类型 | 定义 | 示例 |
|------|------|------|
| **Road** | 道路 | 珞喻路、关山大道 |
| **POI** | 商业主体、地标、机构 | 武汉大学、咖啡厅 |
| **Building** | 建筑、楼层 | 泛悦汇三楼 |
| **Block** | 街区、商圈 | 街道口、光谷步行街 |

### 3.2 关系（8种：空间3 + 语义5）

#### 空间关系（来自shp数据或文本位置信息）

| 关系 | 定义 | Schema约束 | 示例 |
|------|------|------------|------|
| **位于** | A在B处 | (任意, 任意)* | "在珞喻路" |
| **相邻** | A和B邻近 | (POI/Building, POI/Building) | "旁边" |
| **属于** | A是B的一部分 | (任意, POI/街区/区域) | "楼层属于商场" |
| **连接** | A和B通道连接 | (Road, 任意) | "连通" |

*标"任意"表示RE阶段不检查（无类型），PostValidation检查*

#### 语义关系（从小红书文本高频提取）

| 关系 | 定义 | Tail类型 | 示例 |
|------|------|---------|------|
| **推荐指数** | 用户推荐程度 | 推荐度标签 | "超推这家咖啡厅" |
| **适合场景** | 适用场景/人群/时间 | 场景标签 | "最适合约会" |
| **承载活动** | 可进行的活动 | 活动标签 | "很适合拍照" |
| **引发情感** | 引发的情感/氛围 | 情感标签 | "氛围很治愈" |
| **品类特征** | 品类/风格/特色 | 特征标签 | "老字号代表" |

### 3.3 属性系统（扩展）

#### 实体属性

class EntityAttributes(BaseModel):

### 4.4 PostValidation（新增）✨

```python
SCHEMA = {
    "位于": {"head": ["POI", "Building"], "tail": ["Block", "Road", "POI"]},
    "相邻": {"head": ["POI", "Building"], "tail": ["POI", "Building"]},
    "属于": {"head": ["任意"], "tail": ["POI", "Block", "区域"]},
    "连接": {"head": ["Road"], "tail": ["任意"]},
    # ...语义关系无强约束
}

def validate(triple, linked_entities):
    head_type = linked_entities[triple.head].entity_type
    tail_type = linked_entities[triple.tail].entity_type
    schema = SCHEMA.get(triple.relation)
    return head_type in schema["head"] and tail_type in schema["tail"]
```

**预期**：Schema违反率降低 >40%

## 十、关键问题解答

**Q: NER无分类会不会遗漏实体？**
A: 不会。反而因为任务简化，准确率反而更高。类型信息由Linking补充。

**Q: Linking失败（无OSM记录）怎么办？**
A: 标记为UNKNOWN或新实体候选，可单独处理或做数据补充。

**Q: 这个方案迁移到其他城市容易吗？**
A: 完全容易。只需换OSM数据库，整个逻辑通用。

**Q: 关系定义是否固定？**
A: 关键的8个是核心。可根据新的小红书数据模式补充S，但不需要改existing ones。

**Q: 什么时候考虑方案C（完整社交语义）？**
A: 先验证核心方案有效（效果>85%），再逐步加S3-S12。
