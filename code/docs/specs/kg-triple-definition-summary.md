# 地理知识图谱三元组定义总结

更新时间：2026-04-10

---

## 一、核心设计原则

1. **关系抽取不关心实体类型** - 提示词中不描述类型约束，关系语义独立于实体类型
2. **地理实体仅提取名称** - 类型信息通过Linking从OSM获取
3. **概念实体需要识别类型** - OSM中无概念实体，需新建节点
4. **情感/评价属性化** - 避免节点爆炸
5. **Tail类型统一为实体节点** - 所有关系的Tail都是图谱中的节点，而非字面值
6. **避免复合结构** - 拆解为标准三元组，降低抽取难度

## 二、实体处理策略

### 2.1 地理实体（仅提取名称）

| 实体类型 | 来源 | 处理方式 |

| POI | OSM + 文本补充 | Linking到OSM，匹配失败则新建 |
| 建筑物 | OSM + 文本补充 | Linking到OSM，匹配失败则新建 |
| 街区 | OSM + 文本补充 | Linking到OSM，匹配失败则新建 |
| 道路 | OSM预加载 | 不创建，仅关联 |
| 行政区划（区域） | OSM预加载 | 不创建，仅关联 |

## 三、关系定义（12个）

### 3.1 空间关系（4个）

> 补充性关系，主要从shp数据计算，文本提及则抽取

| 关系 | 语义定义 | 方向规则 | 关系属性 | 示例 |
|------|----------|----------|----------|------|
| **位于** | A在B处 | 较小实体→较大实体 | - | <咖啡厅, 位于, 街道口> |
| **相邻** | A和B空间邻近 | 同级实体间 | **联动推荐**（布尔） | <咖啡厅, 相邻, 书店> [联动推荐=true] |
| **属于** | A是B的组成部分 | 子实体→父实体 | - | <行政楼, 属于, 武汉大学> |
| **连接** | A和B交通连接 | 道路→地理实体 | - | <珞喻路, 连接, 光谷> |

> **相邻关系属性说明**：
> - 联动推荐=true：文本显式提及组合推荐意图（"逛完可以去对面..."）
> - 联动推荐=false或无属性：仅表达空间邻近，不带推荐意图

### 3.2 社交语义关系（5个）

> 重点抽取的关系，捕捉用户推荐、体验、评价等维度
> **设计原则：Tail统一为实体节点，避免复合结构；适合人群/场景改为实体属性**

| 关系 | 语义定义 | Tail实体类型 | 关系属性 | 示例三元组 |
|------|----------|--------------|----------|-----------|
| **推荐指数** | 用户对场所的推荐程度 | 评价等级节点 | - | <咖啡厅, 推荐指数, 超推> |
| **承载活动** | 场所能进行的活动 | 活动节点 | **时段**（可选） | <咖啡厅, 承载活动, 拍照> |
| **可达方式** | 到达场所的交通方式 | 交通方式节点 | - | <咖啡厅, 可达方式, 地铁> |
| **消费档次** | 消费水平 | 消费等级节点 | - | <咖啡厅, 消费档次, 中档> |
| **品类特征** | 风格/文化特征 | 特征标签节点 | - | <咖啡厅, 品类特征, 老字号> |

### 3.3 对比关系（3个）

> 表达场所间的对比评价，维度作为关系属性绑定对比对象

| 关系 | 语义定义 | Tail实体类型 | 关系属性 | 示例三元组 |
|------|----------|--------------|----------|-----------|
| **优于** | A在某方面好于B | 地理实体节点 | **维度**（列表） | <咖啡厅, 优于, 隔壁店> [维度=["价格", "品质"]] |
| **相似** | A和B在某方面相似 | 地理实体节点 | **维度**（列表） | <咖啡厅, 相似, 书店> [维度=["风格"]] |
| **劣于** | A在某方面不如B | 地理实体节点 | **维度**（列表） | <咖啡厅, 劣于, 星巴克> [维度=["环境"]] |

> **注**：原"相比对象"+"优势维度"拆解方案已改为对比关系+维度属性，语义绑定更完整

## 四、关系详细说明

### 4.1 推荐指数

**语义**：用户对场所的整体推荐程度

**Tail实体**：评价等级节点（预定义枚举值作为节点）

| 节点名称 | 语义 | 典型表达 |
|---------|------|---------|
| 超推 | 强烈推荐 | "超级推荐"、"一定要去"、"必去" |
| 推荐 | 正面推荐 | "不错"、"值得去"、"挺好的" |
| 一般 | 中性评价 | "还可以"、"一般般"、"还行" |
| 不推荐 | 负面评价 | "不建议去"、"踩雷"、"避雷" |

**典型文本**：
- "超推这家咖啡厅，氛围感拉满" → <咖啡厅, 推荐指数, 超推>
- "不太建议去，人太多体验不好" → <咖啡厅, 推荐指数, 不推荐>

### 4.2 承载活动

**语义**：在场所可以进行的典型活动

**Tail实体**：活动节点

**关系属性**：

| 属性名 | 类型 | 说明 | 示例值 |
|--------|------|------|--------|
| 时段 | 时间概念（可选） | 该活动最适合的时间段 | 周末、晚上、樱花季 |

| 活动节点示例 |
|-------------|
| 拍照、打卡、逛街、就餐、喝咖啡、约会、聚会、办公、休息、购物、观影 |

**典型文本**：
- "很适合拍照和聚餐" → <咖啡厅, 承载活动, 拍照>, <咖啡厅, 承载活动, 聚餐>
- "周末很适合来打卡" → <咖啡厅, 承载活动, 打卡> [时段=周末]
- "晚上灯光很漂亮，适合散步" → <公园, 承载活动, 散步> [时段=晚上]
- "樱花季一定要来" → <武汉大学, 承载活动, 赏花> [时段=樱花季]

**图数据库实现**：

```cypher
// Neo4j - 带属性的关系
CREATE (c:POI {name: "咖啡厅"})
CREATE (a:Activity {name: "拍照"})
CREATE (c)-[:承载活动 {时段: "周末"}]->(a)
```

**设计说明**：时段修饰的是**特定活动**而非场所本身，因此作为承载活动关系的属性。这保留了时段-活动的绑定关系，同时避免引入复合结构或独立关系。

### 4.3 可达方式

**语义**：到达场所的交通方式

**Tail实体**：交通方式节点

| 交通方式节点示例 |
|-----------------|
| 地铁、公交、步行、自驾、骑行、打车 |

**典型文本**：
- "地铁直达很方便" → <咖啡厅, 可达方式, 地铁>
- "开车过去有停车场" → <咖啡厅, 可达方式, 自驾>
- "步行10分钟就到了" → <咖啡厅, 可达方式, 步行>

### 4.4 消费档次

**语义**：场所的消费水平

**Tail实体**：消费等级节点（预定义枚举值作为节点）

| 节点名称 | 语义 | 参考标准 |
|---------|------|---------|
| 平价 | 经济实惠 | 人均50以下 |
| 中档 | 适中消费 | 人均50-150 |
| 高档 | 较高消费 | 人均150-300 |
| 奢侈 | 高端消费 | 人均300以上 |

**典型文本**：
- "人均80-100，档次不低" → <咖啡厅, 消费档次, 中档>
- "性价比不错，平价消费" → <咖啡厅, 消费档次, 平价>

### 4.5 品类特征

**语义**：场所的风格、历史或文化特征

**Tail实体**：特征标签节点

| 特征标签节点示例 |
|-----------------|
| 老字号、新潮、网红、小众、文创、民俗、复古、ins风、日式、中式 |

**典型文本**：
- "是武汉老字号的代表" → <咖啡厅, 品类特征, 老字号>
- "装修很ins风，适合拍照" → <咖啡厅, 品类特征, ins风>

### 4.6 优于

**语义**：A在某方面好于B

**Tail实体**：地理实体节点（POI/建筑物/街区）

**关系属性**：

| 属性名 | 类型 | 说明 | 示例值 |
|--------|------|------|--------|
| 维度 | 列表 | A优于B的方面 | ["价格", "品质", "环境"] |

| 对比维度示例 |
|-------------|
| 价格、环境、服务、人流量、品质、氛围、交通、停车、口味 |

**典型文本**：
- "比隔壁那家便宜又好吃" → <咖啡厅, 优于, 隔壁店> [维度=["价格", "口味"]]
- "相比街道口，这里人少环境好" → <咖啡厅, 优于, 街道口> [维度=["人流量", "环境"]]

### 4.7 相似

**语义**：A和B在某方面相似

**Tail实体**：地理实体节点（POI/建筑物/街区）

**关系属性**：

| 属性名 | 类型 | 说明 | 示例值 |
|--------|------|------|--------|
| 维度 | 列表 | A和B相似的方面 | ["风格", "价位"] |

**典型文本**：
- "和隔壁店风格差不多" → <咖啡厅, 相似, 隔壁店> [维度=["风格"]]
- "这两家价位差不多，但这家环境更好" → <咖啡厅, 相似, 隔壁店> [维度=["价位"]]

### 4.8 劣于

**语义**：A在某方面不如B

**Tail实体**：地理实体节点（POI/建筑物/街区）

**关系属性**：

| 属性名 | 类型 | 说明 | 示例值 |
|--------|------|------|--------|
| 维度 | 列表 | A劣于B的方面 | ["环境", "服务"] |

**典型文本**：
- "不如星巴克环境好" → <咖啡厅, 劣于, 星巴克> [维度=["环境"]]
- "这家服务比对面差" → <咖啡厅, 劣于, 对面店> [维度=["服务"]]

## 五、抽取流程

```
┌─────────────────┐
│  NER（简化版）   │  地理实体：仅名称
│                 │  概念实体：名称+类型
└────────┬────────┘
         ↓
┌─────────────────┐
│ Entity Linking  │  地理实体→Top5+LLM→OSM
│                 │  概念实体→新建节点
└────────┬────────┘
         ↓
┌─────────────────┐
│  RE（关系抽取）  │  无类型约束
│                 │  提取语义三元组
│                 │  Tail统一为实体节点
└────────┬────────┘
         ↓
┌─────────────────┐
│ Eval + 校验     │  幻觉检查
│                 │  方向校验（需类型）
└────────┬────────┘
         ↓
┌─────────────────┐
│  Label（属性）   │  情感标签、体验评价
│                 │  聚合统计
└─────────────────┘
```

## 六、校验规则

### 6.1 幻觉检查（不需要类型）

- head/tail是否在原文中出现
- 关系是否有文本证据支撑

### 6.2 方向校验（需要类型）

**实体层级**：
```
概念实体(0) < POI/建筑物(1) < 街区/道路(2) < 区域(3)
```

**空间关系方向**：
| 关系 | 方向规则 |
|------|----------|
| 位于 | head_level ≤ tail_level |
| 相邻 | head_level = tail_level |
| 属于 | head_level ≤ tail_level |
| 连接 | head是道路 |

**语义关系方向**：

| 关系 | 方向规则 |
|------|----------|
| 承载活动 | 地理实体 → 活动概念 |
| 可达方式 | 地理实体 → 交通方式概念 |
| 推荐指数 | 地理实体 → 评价等级 |
| 消费档次 | 地理实体 → 消费等级 |
| 品类特征 | 地理实体 → 特征标签 |
| 优于 | 地理实体 → 地理实体 |
| 相似 | 地理实体 → 地理实体 |
| 劣于 | 地理实体 → 地理实体 |

> **注**：适合人群/场景已改为实体属性，不再作为关系抽取

## 七、属性聚合

实体属性从多条文本聚合统计：

| 属性 | 来源 | 聚合方式 |
|------|------|----------|
| 推荐热度 | 推荐指数关系 | 加权平均 |
| 适合对象 | 文本提取 | 频次排序，TopN |
| 常见活动 | 承载活动关系 | 频次排序 |
| 最佳时段 | 承载活动.时段 | 频次排序 |
| 消费水平 | 消费档次关系 | 多数投票 |
| 品类标签 | 品类特征关系 | 集合合并 |
| 情感标签 | 文本提取 | 频次排序 |
| 知名度 | 文本推断 | 综合判断 |

### 7.1 适合对象属性设计

**属性名**：适合对象

**类型**：列表（字符串数组）

**示例值**：["情侣约会", "亲子游玩", "学生打卡", "商务办公", "独处放松"]

**抽取规则**：
- 从文本中识别"适合XX"表达
- 合并人群+场景为一个标签（如"情侣约会"、"亲子游玩"）
- 多条文本聚合后按频次排序取TopN

**聚合实现**：
```json
{
  "name": "咖啡厅",
  "type": "POI",
  "适合对象": ["情侣约会", "学生打卡", "办公"],
  "适合对象频次": {"情侣约会": 15, "学生打卡": 8, "办公": 5}
}
```

## 九、设计调整说明

### 9.1 Tail类型统一化

**问题**：原设计中部分关系Tail为标签值（如"超推"、"中档"），部分为实体节点，导致不一致。

**调整**：所有Tail统一为实体节点。枚举值（如超推、中档、老字号）也作为预定义节点存在于图谱中。

**收益**：
- 图谱结构统一，所有三元组都是 `<实体, 关系, 实体>`
- 支持反向查询（如"哪些场所被评为超推"）
- 支持节点属性扩展（如评价等级节点可有"权重"属性）

### 9.2 对比关系重构

**问题**：原设计中"相比对象"+"优势维度"拆解为独立关系，但语义断裂——无法表达"价格优势是对比隔壁店的结果"。

**调整**：改为对比关系（优于/相似/劣于）+ 维度属性，维度与对比对象绑定。

| 原方案 | 新方案 |
|--------|--------|
| `<咖啡厅, 相比对象, 隔壁店>` + `<咖啡厅, 优势维度, 价格>` | `<咖啡厅, 优于, 隔壁店>` [维度=["价格"]] |
| 语义断裂，维度无法绑定对比对象 | 维度作为属性，语义完整 |

**收益**：
- 维度与对比对象绑定，语义完整
- 支持反向查询（如"哪些场所被评价为优于隔壁店"）
- 抽取更直观，LLM一次提取对比关系+维度

### 9.3 相邻关系属性化

**问题**：原设计中"周边联动"与"相邻"语义重叠，LLM抽取不稳定。

**调整**：删除"周边联动"关系，将联动推荐意图作为"相邻"关系的属性。

| 原方案 | 新方案 |
|--------|--------|
| `<咖啡厅, 相邻, 书店>` + `<咖啡厅, 周边联动, 书店>` | `<咖啡厅, 相邻, 书店>` [联动推荐=true] |

**收益**：
- 空间关系统一，减少关系数量
- 联动推荐意图与空间邻近绑定
- LLM抽取更稳定

### 9.4 适合场景属性化

**问题**：原设计中"适合场景"关系抽取不稳定，LLM难以区分活动与场景；人群/场景作为实体节点可能冗余。

**调整**：删除"适合场景"关系，改为实体属性"适合对象"，合并人群+场景为一个标签。

| 原方案 | 新方案 |
|--------|--------|
| `<咖啡厅, 适合场景, 约会>` + `<咖啡厅, 适合场景, 情侣>` | 实体属性：适合对象=["情侣约会", "学生打卡"] |

**收益**：
- 减少关系数量，图谱更简洁
- 人群+场景合并为复合标签，语义更自然
- 多条文本聚合后频次排序，避免节点爆炸

### 9.5 时段作为关系属性

**问题**：原设计中"适合时段"作为独立关系，但时段实际修饰的是**特定活动**而非场所本身。

**调整**：删除"适合时段"关系，将时段作为"承载活动"关系的属性。

**示例**：
- 原：<咖啡厅, 适合时段, 周末> + <咖啡厅, 承载活动, 拍照>
- 现：<咖啡厅, 承载活动, 拍照> [时段=周末]

**收益**：
- 保留时段-活动的绑定关系
- 避免信息丢失（"周末适合拍照"被正确表达）
- 图谱结构更简洁

### 9.6 时段标准化层级

**新增设计**：时段属性按层级标准化，避免冗余。

| 层级 | 规则 | 示例 |
|------|------|------|
| L1：周期 | 直接标准化为枚举值 | 周末、工作日、节假日 |
| L2：时段 | 归一化到6个时段 | "上午10点"→上午，"傍晚"→晚上 |
| L3：季节 | 直接标准化为枚举值 | 樱花季、春季、夏季 |
| L4：事件 | 作为特殊时段节点保留 | 樱花节（可能需年份/地点属性） |

**收益**：
- 避免时段值冗余（如"上午10点"与"上午"）
- 支持时段聚合统计

## 十、注意事项

1. **空间关系优先从shp计算**：文本提及则抽取，但主要依赖空间数据
2. **情感标签属性化**：不作为关系，避免节点爆炸
3. **枚举值作为节点**：评价等级、消费等级、特征标签等枚举值预定义为节点
4. **时段作为关系属性**：时段修饰活动，存储在承载活动关系的属性中，按L1-L4层级标准化
5. **校验后置**：类型校验在Linking后进行，不在抽取阶段约束
6. **对比关系带维度属性**：优于/相似/劣于关系的维度作为属性，绑定对比对象
7. **相邻关系带联动属性**：相邻关系可带联动推荐属性表达组合推荐意图
8. **适合对象作为实体属性**：人群+场景合并为复合标签，多条文本聚合频次排序
